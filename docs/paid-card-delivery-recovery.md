# 已付款但未发卡的密钥故障

支付成功与发卡分开提交，发卡失败不能撤销真实收款。旧库存采用未带版本前缀的 AES-GCM 密文，依赖原 `CARD_DELIVERY_KEY` 或 `CARD_SECRET_SALT`。缺少原密钥时，库存数量和密文非空都不能证明库存可交付。不能用新随机密钥解密旧库存。

## 修复后的行为

- 后台生成博客卡密时，优先使用已存在的 `POINT_CARD_KEY` 写入 `points-v1:` 加密和哈希格式，账户核销、购买发卡、积分发卡均支持该格式。没有版本密钥的部署继续使用原密钥，不更换任何现有密钥。
- 缺少旧密钥时，不把旧格式库存计入可售数量；下单预占还会执行实际 GCM 解密校验。损坏或使用错误密钥的候选卡被跳过，没有可用卡时事务回滚，阻止创建可付款订单。
- 单条历史发卡记录无法解密时，仅显示联系管理员的提示，不让整个订单列表报错，也不把解密异常发给用户。
- 支付后的发卡仍然幂等；维护任务出现未完成发卡时返回非零退出码，供 systemd 记录失败。

## 原密钥无法恢复时

先备份数据库和私密环境配置，核对真实支付成功、订单权益与原预占卡。保留旧密文和历史发卡记录，将不可读取的未售库存停用。对于已付款且尚无发卡记录的订单，在原订单内替换为同商品、同权益的新卡，再执行幂等补发；不重复收费、不把卡密提前核销，不自动改为其他授权来源。

已交付的历史卡密不得批量重置、重复发放或增加权益。无法恢复的历史密钥不能通过部署代码还原，需要管理员根据订单单独处理。支付和设置加密密钥、旧 App 授权数据库、设备绑定规则均保持原值。
