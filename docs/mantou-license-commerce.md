# 商城与积分发放应用授权卡密

后台「卡密管理 → 商品管理 → 新建」选择 **Mantou Admin 应用授权**，设置介绍和售价，保存后到「生成卡密」选择商品添加库存。后台「积分兑换」也可创建相同来源的商品，设置积分、添加库存后开放兑换。两种商品分别管理库存，均使用原 Mantou Admin 授权数据。

生成库存先在原授权数据库注册 16 位卡密，再把同一张卡的加密副本及唯一 `legacyCardId` 写入博客库存。可导入原库已存在且未使用、未绑定的卡密；同一卡不能重复加入多个库存。生成后仅为库存，发售不会提前标记原卡已使用。用户在 App 内输入卡密完成设备绑定，原客户端协议和签名服务不变。博客显示的卡号用于订单查询，App 只需要卡密。博客账户核销接口拒绝应用授权卡。

购买时预占库存，支付成功后交付；积分扣除、库存领取、订单和发卡记录在博客的同一个事务内完成，失败全部回滚。已交付的卡密可在原订单或积分兑换记录再次查看。领取前检查原授权卡未使用、未绑定且明文一致；授权数据库不可用时停止发放。已支付订单由维护任务重试，不重复发卡。

两个数据库不能使用同一个事务。若原库生成成功而博客入库失败，卡密保留在应用授权后台，可重新导入；不在网络失败时补偿删除，避免误删已经写入的卡密。已有商城库存关联的授权卡不能从应用授权后台删除、重置或手动绑定。管理员明确解除设备绑定的能力仍保留。

应用授权的卡密本身没有旧库到期字段，不能设置博客卡密有效期。设备绑定到期由「应用与设备授权」统一控制。首次启用时固定历史绑定最大编号，之前的绑定永久保留，之后的新绑定才计时；调整天数或关闭后重开不改变这个边界。

## 上线与回滚

新增迁移 `20261017090000_mantou_license_commerce` 仅向博客添加可空唯一 `cards.legacyCardId` 和两个默认 `BLOG` 的来源字段，不改动旧授权库。历史商品与发卡记录保持原用途，不自动转换、生成售价或发布积分商品。`POINT_CARD_KEY` 必须沿用现有值，不能轮换；生产支付与设置加密密钥也不变。

生产维护任务访问 `/api/cron/expire-orders`，仅接受私密 `Authorization: Bearer ...`，不接受 URL 密钥。任务每 5 分钟运行，重试支付发卡、清理未付订单、分批解除到期的新绑定。首次启用必须保存历史编号边界；没有边界时到期任务安全跳过。

回滚代码前先暂停新建的应用授权商品和积分兑换，避免旧代码把通用类型当作博客核销卡。新增列可保留；不要删除历史发卡记录、原授权卡或加密密钥。

维护脚本为 `scripts/run-maintenance.mjs`，只连接本机，禁止跟随重定向，超时 55 秒；不会把密钥放在命令行或 URL。服务器使用 `ops/systemd/cloudmantou-maintenance.{service,timer}`，可用 `systemctl list-timers cloudmantou-maintenance.timer` 查看下次运行时间。替换发布目录时保留同一份私密 `.env`。
